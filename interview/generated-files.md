# What Phase 1 generates

*Status: written (O2, 2026-10-13); template paths updated by O3b 2026-10-13 (macro files, the pace gate, the tests);
the column "If the house already has one" and the backlog rule for an existing house (KIT-EXIST.c, 2026-10-31). The
contract between the interview and `templates/`. Read by the agent at topic 11 of the Phase 1 interview, and in
Phase 2 whenever a topic is still `pending`.*

## The rules of generation

1. **Generated once, then owned by the house.** Every file below is written at the end of Phase 1, except the
   rows marked "copied by its backlog item": those (the packages, macros, export, guard, pacing and tests) are
   copied and filled when that item is built, after the box is reachable read-write, never at the end of Phase 1.
   Each is the house's from then on; later sessions edit it by hand under the document standard. The profile stays the record
   of what was answered. When an answer changes, the change is a backlog item that updates both the profile and
   the derived file, with a CHANGELOG entry. Never regenerate over a hand-edited file.
2. **From a template where one exists, from the principle where none does.** The template column names the file
   in `templates/`; "written" means the agent writes the file from the section list below and the profile.
3. **Every generated file opens with a status line**: the date, "generated by the Phase 1 interview", and the
   profile fields it was made from. Values the profile left `pending` are written as `(pending: topic N)`, never
   invented.
4. **Nothing secret, nothing live.** Generated files carry no codes, numbers or addresses, and no entity id that
   was not read from the box in topic 0.
5. **Plain words in the manual, ids in the wiki.** The manual is for the household; the wiki is for the builder.
6. **Adoption, not replacement (an existing house, `setup.existing_house: true`; `AGENTS.md` "Phase 0E" rule 5).**
   The column "If the house already has one" says what each file records when the house brought its own version
   of the thing. The rule behind every cell: the house's existing scheme is written down beside the kit's and
   kept; the kit's way applies to new work from the adoption date; a build item is generated only where nothing
   equivalent exists; what the house could change some day is a tidy-up row (`templates/docs/backlog.md`,
   "Tidy-up"), never a generated build item. Nothing is renamed, rewritten or re-raised to fit a template.

## Section lists for the written files

**`docs/naming.md`**
1. Areas and floors, as the box has them, with the kind of each (shared, private, child, outdoor, utility).
2. The house's words: presence modes, guest mode, modes, nicknames; the reserved words and why each is reserved
   (on an existing house, read from the inventory: an alarm's arm modes, a mode select's options).
3. Automations and scripts: `Category - Target`; the category list this house starts with (Lighting, Motion
   Lighting, Notify, Health, Presence, Climate, and whatever topic 3 implies), with one example each using the
   house's own areas. On an existing house, first the legacy line: the pattern the inventory found the house uses
   most, with its count ("legacy: `<Area> <thing>`, kept; 61 of 80 automations"), and the date from which new
   work follows `Category - Target`; the two live side by side and no rename is proposed.
4. Helpers: the plain name for the person-facing one, the suffix for a hidden companion; check before creating.
5. Ids: decided at creation, read back, never guessed; select by name and id, never by prefix.
5b. Names typed at creation, so the id follows: devices `<Area> <Thing>` ("Front Porch Light", so the id becomes
   `light.front_porch_light`); sensors `<Area> <Thing> <What>` ("Kitchen Sink Leak"); a Matter or vendor device
   is renamed at commissioning, before anything refers to it. A plan writes the intended name and marks each id
   "(read back)" until the live export (`export/entities.json`) shows it; the build replaces the mark with the id.
6. Labels: the readable record of membership, kept here.
7. YAML key order.

**`docs/policies.md`**
1. What the agent may do without asking (`agent.may`), what it asks first (`agent.ask_first`), what it never does
   (`agent.never` plus the standing list in `AGENTS.md`).
2. The design-only areas for this house: the safety list from topic 3, plus alarm behavior, locks and codes,
   consent, firmware and version changes. Each gets a design with a build plan, never an unattended build.
3. Voice: who may use it, which rooms, what is exposed (lights, switches, scene scripts), what is never exposed.
4. Presence: who counts, the failure direction ("the house does not arm itself" is the visible failure), the
   per-person toggle, thermostat occupancy ignored; how each sitter and visitor gets in (`people[].entry`) and
   whether the house notices the door during their usual window, told to the owners only (`people[].door_notice`).
5. Priorities in order, "never" list, "must work without Home Assistant" list.
6. Unattended work: allowed or not, the budget gate, drafts only, the push guard.
7. Where this house differs from the kit (an existing house; `AGENTS.md` "Phase 0E" rule 6; `levels.md`
   `E0-differs-written`). Headed `Where this house differs from the kit`, word for word (a list number in front is
   fine). A standing table, one row per difference, or the words "none yet" when nothing differs:

   | The kit's rule | What this house does | The house's choice | Since |
   |---|---|---|---|
   | (`principles/<file>.md` rule n) | (one line) | stands / tidy-up row `<id>` / safety row `<id>` | date |

   Three outcomes, nothing else. **Stands** is the default: recorded once, new work built the kit's way, never
   argued again (a naming scheme that is not `Category - Target`; a presence mode called "Away" beside an alarm
   with an Away arm mode, so the kit's new work uses another word; a `notify.*` call per automation instead of one
   router; settable things on a dashboard's first tab). **A tidy-up row** when the person says they want it changed
   some day; nothing moves until they take the row. **A safety row** when the difference is on the kit's safety
   list (`principles/safety-and-security.md` rule 19: an arm, disarm, lock, unlock or code change with no person's
   act, except as rules 4 and 16 allow; a message
   to a person the owner never named; a secret in the repository or the configuration; no backup off the box; no
   second factor for an administrator): said once, plainly, with the fix on offer, the person decides; the row
   stays on the backlog's first page and in the level 0 and level 1 lines it maps to until it is done or the person
   writes `accepted: <why>` on it, which the test then reports as `skipped` with the reason, never as `pass`. The
   agent never fixes a difference to make a test pass, never renames anything to fit a rule, and never re-raises a
   "stands" row in a later session.

**`docs/notifications.md`**
1. The classes and the level each needs; the default class when a caller names none.
2. Each phone: label, level, minor or not (Dismiss only), platform. Until a person sets their level in the UI,
   the router treats that phone as "Everything"; the backlog carries "each person sets their own level" (the
   owner sets a minor's). A person with no phone or no app (a child's tablet without it) is not a phone here and
   cannot get even life-safety pushes: say who tells them.
3. Life safety: everyone, always, ignoring levels and quiet hours.
4. Quiet hours and which classes they silence.
5. The maintainer class: owner only.
6. Speech surfaces, if any; panel first, speakers only when the panel cannot.
7. Guests and sitters: what they get, the time box, plain words.
8. The second channel, if planned: a design-only item with consent rules, not built here.
9. Tags and replacement slots this house will use (alarm state, power, leak, battery, backup). On an existing
   house, first the paths that already exist: which notify service reaches which phone, by role, and the tag or
   router scheme the first look found, kept as they are; the classes apply to new work.
10. The test rule: the owner sends the first of every new message. Test mode (`input_boolean.notify_test_mode`):
    the owner switches it on before any simulated-state test, so production automations log instead of push;
    life safety still delivers, so a smoke, CO or flood trigger is never simulated; it switches itself off after
    two hours and is a health notice while on.

**`docs/health-checks.md`**
1. Subsystems and their counts (security, plumbing, system, network, radio; whichever topic 3 implies).
2. Checks per device class present in the house, with faults versus notices and the starting thresholds, each
   held in a helper (battery, silence, unavailable, backup age, off-box copy age, mesh "x of y online", disk use
   and processor temperature via the System Monitor integration, an integration that must stay loaded). Off-box
   copy age: the built-in "last successful automatic backup" sensor is only stamped when every configured
   location took the upload, so one `age` check on it covers the off-box copy, provided the automatic backup is
   set to include the off-box location; say so here, or "not monitorable" in section 6 if it is not.
3. Watching the watchers: the automations whose disabled state is itself a fault.
4. Planned-restart suppression.
5. The daily offline reminder.
6. What is not monitored on purpose.
7. On an existing house, `equivalent:` lines: for each subsystem the house already watches, the entity that
   carries the count and the dashboard or message that shows it, so the kit's package covers only the rest and
   levels 3 and 4 read the house's own check as the evidence.

**`docs/operations.md`**
1. Backup tiers this hardware allows, what each protects against, the measured restore time (to be filled by the
   first drill), the off-box copy, the monthly drill. On an existing house, also the backup locations by kind and
   the schedule as the inventory found them, and the existing repository (`setup.existing_repo`: a host kind,
   private or not; never an address) as the configuration mirror of record until a tidy-up row folds it in.
2. Freezes: the calendar from topic 9, what a freeze allows (fixes only), what it forbids (firmware, versions,
   new automations), and the away buffer.
3. Staging: the clone or the drill, when a change goes there first.
4. Pacing: the probe, the pace line, the buffer, the gate before every unattended run, the review cadence.
5. The push guard: what it scans for, that it exits non-zero.

## Backlog items the generation always adds

**Ahead of the first request**, only the ones it needs (each is small, and the first request cannot be built or
tested without it): agent access if `setup.agent_access` is not written (1; `install/agent-access.md`), packages
enabled in `configuration.yaml` (1), the radio bring-up for each radio in `setup.radios` that has no working network
yet (3 each; `adapters/radios/`), the voice bridge if the request is spoken (2; `adapters/voice/`).

**After the first request**, in this order, sized: notification router (3), first health count (3), backup restore
drill (1; "Needs first: a drill target" on a one-box house with no spare boot drive), manual first chapter (2), live
export script (2; copy `templates/export/export_house.py` to `house/export/`, which the documentation principle
treats as the truth), push guard as a pre-push
hook (1; `templates/guard/`), usage probe and budget gate if unattended runs are wanted (2), wiki schema pages for
the first integrations (3), the sitter track when a sitter or regular visitor is first expected (2). Then the whole-home items: a house-records inbox and first walk-around of labels and shutoffs (2; `principles/house-records-and-equipment.md`), and the maintenance calendar with its first recurring tasks (2; `principles/maintenance-calendar.md`). Items whose
topic is `pending` carry "Needs first: topic N".

**On an existing house** (`setup.existing_house: true`), the two lists above are read against the inventory and
the first look before anything is written: an item is generated **only where nothing equivalent exists**. The
house already notifies people: no router item (a tidy-up row "one router, when you want one"). It already counts
unavailable things on a dashboard: a health item only for the subsystems with no `equivalent:` line. It already
keeps a manual or a wiki: the kit's skeleton is a tidy-up row, the existing pages stay. The live export is always
an item (the export already ran in Phase 0E; its item schedules it, so `E0-inventory` stays fresh). The push guard
and, when wanted, the usage probe are always items (they are the agent's, not the house's). The restore drill is
always an item when the first look's check 4 found no proven restore. Every item the house already has an
equivalent of goes to the tidy-up section instead, with the equivalent named in its "From" cell, so a later session
can see why it was not generated and never generates it again.

**The person's other ideas** go after the item they depend on, each with "Needs first: <item>". When a generated
item already does what an idea asks (a weekly battery report is the first health count), keep one item, named after
the person's words.
